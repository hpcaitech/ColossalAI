## 实际测试范围

两份官方代码快照：
- Ouro-1.4B：`574fa66cb8bf5abdc979642d01cf2b79b16bfab1`
- Ouro-2.6B：`1ed04250da1a9936042725d302e81c8fa2ab5abd`

均为随机初始化 tiny config：2 层、hidden size 64、词表 128、batch 2、序列 16。
本次未加载官方预训练权重，未测试原始参数规模，也未测试收敛。

每次 forward 都用 hook 验证每个 decoder layer 实际被调用 2/4 次；

因此这里验证的是插件行为，不能替代官方代码与适配层本身的独立对照。

共享工具的判据、容差和 precision recipe 均未改动。

## 未通过及定位

### 1. Gemini 默认小模型 chunk + 双卡梯度累积

- 默认 chunk 搜索在该 tiny 模型上使用 keep_gathered 路径。
- 2 卡、全局 4 个 micro-batch（每卡累积 2 个）、4 次循环：25/27 梯度失败，
  最大相对 L2 误差约 73.6%，超过工具约 8.29% 的统一上界。
- 同一模型同一配置改成每卡 1 个 micro-batch：27/27 通过。
- 同样 4 个 micro-batch，改成显式分片 chunk：27/27 通过。
- 1 次循环的额外对照也失败（23/25，最大误差约 76.0%），说明该问题不要求多次循环才能触发。
  该对照冻结了单循环下无梯度贡献的 exit gate。最初未冻结 gate 的探测在单卡参考运行时
  被 Gemini 的缺梯度检查拒绝，原始 error 报告同样保留，不当作数值比较结果。
- 对应工具文档记录的 Gemini 多卡累积问题 #6496；本次进一步发现它与此处 chunk 配置有关。
  尚未对通用实现做修复，不把显式分片的通过当作默认配置的通过。

关键报告：
- 失败：`run-20261104-130651-FPysIK/report.json`
- 不累积对照：`run-20261104-130732-RVYCDg/report.json`
- 分片对照：`run-20261104-130403-FnitwZ/report.json`
- 单循环冻结 gate 对照：`run-20261104-130858-0YfZm9/report.json`
- 最初单循环缺梯度错误：`run-20261104-130809-QpGwY2/report.json`

### 2. ZeRO-2 BF16 checkpoint 续训不一致

2+2 步对连续 4 步，有 22 个训练条目不同（21 个参数和最后一步 loss）。
参数最大绝对差 0.00390625；最后一步 loss 相对差约 1.59%。
FP32 的对应训练比较全部一致。

源码中低精度模型加载后调用 update_master_params，从 BF16 working weights 重建 FP32 master weights；
优化器 checkpoint 保存的是 Adam 状态，未保存这份精细的主权重。
这与工具文档的 #6490 一致。误差来源判断有源码支持，但本次没有改代码做修复后验证。

报告：`run-20261104-130513-KLiToU/report.json`、`trace-differences.json`。

### 3. Gemini 分片 checkpoint 加载报错

恢复模型时出现：
`TypeError: GeminiDDP.named_parameters() got an unexpected keyword argument 'remove_duplicate'`。

GeneralCheckpointIO 调用 named_parameters(remove_duplicate=False)，当前 GeminiDDP 的同名方法
只接收 prefix/recurse。这是共享 checkpoint 接口不匹配，对应工具文档的 #6497。

报告：`run-20261104-130542-FUDUdF/report.json`。

### 4. HF 导出回读的测试接入差异

工具默认 `model_cls.from_pretrained(path)` 没有指定 eager，触发当前适配层的明确限制。
因此 FP32 的通用 resume 报告为 29/30，唯一失败项是 HF 回读，不是训练状态恢复。

补充按已支持的方式 `from_pretrained(path, attn_implementation="eager")` 回读：
FP32、BF16 两份导出权重均 27/27 逐位一致。原始失败报告没有改写；
补充结果在各自运行目录的 `reload-eager.json`。
BF16 导出权重可读回，并不消除它的继续训练不一致问题。

## 原始统计与尚未覆盖

24 次模型探测：18 passed、4 failed、2 error；包含上面说明的单循环诊断设置错误。
此外有 2 次显式 eager 重载检查，各 27/27 通过；GPU 预检单独保留。
这些是开发探测记录，不是完整 L1/L2 验收报告。

尚未完成：正式 model_zoo 注册、TorchDDP / FSDP 矩阵、梯度检查点、lazy init、
offload 矩阵、真实尺寸/官方权重，以及完整 L1/L2 覆盖。
当前适配层本身明确拒绝尚未验证的 gradient checkpointing。

## 复现

在 `wzj-colossalai-2d4` 容器内，确认 GPU 空闲后运行：

```bash
cd /workspace/ColossalAI
# 核心多循环对照，通过
CUDA_VISIBLE_DEVICES=0,1 bash scripts/phase2/2d4/run.sh --scenario independent --model ouro14 --loops 4 --plugin zero2_fp32 --world-size 2 --steps 3

# Gemini 默认 chunk 的多卡累积失败
CUDA_VISIBLE_DEVICES=0,1 bash scripts/phase2/2d4/run.sh --scenario dp --model ouro14 --loops 4 --plugin gemini_bf16_default --world-size 2 --micro-batches 4

# ZeRO BF16 续训不一致
CUDA_VISIBLE_DEVICES=0,1 bash scripts/phase2/2d4/run.sh --scenario resume --model ouro14 --loops 4 --plugin zero2_bf16 --world-size 2

# Gemini checkpoint 加载失败
CUDA_VISIBLE_DEVICES=0,1 bash scripts/phase2/2d4/run.sh --scenario resume --model ouro14 --loops 4 --plugin gemini_bf16 --world-size 2
```

主机上建议使用同目录 run_host.sh，它会持有现有 CI GPU 锁并再次检查占用。
